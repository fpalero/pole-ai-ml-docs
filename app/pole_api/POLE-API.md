# pola_api — HTTP API Reference

> Canonical endpoint reference for the `pola_api` FastAPI application
> (source: `app/pola_api/`). Generated by the team-lead from the current
> source code — every route, parameter, schema and error code below is taken
> directly from the routers/controllers, Pydantic schemas, services and tests,
> not inferred.

This document covers **all HTTP endpoints** plus the two **WebSocket**
endpoints (chatbot and training chatbot). It is the single source of truth for
the REST surface; the older `docs/app/pola_api/flows.md` describes the *user
workflows* and is kept aligned with this document (Phase 11 regeneration,
ticket `PAIML-POLA-API-020`).

---

## 1. Overview

`pola_api` is the orchestration backend of the pole-ai pipeline. It is split
into six slices, all mounted under the `/api` prefix (plus one root health
route and two WebSocket routers):

| Slice | Router prefix | Description |
| :--- | :--- | :--- |
| System | `/health` (no `/api`) | Liveness probe. |
| Tools | `/api/tools` | Crop / shift / correct + histogram analysis/read/patch/summary (background jobs) + health. |
| Chatbot | `/api/chatbot` | Video-analysis ReAct chatbot over WebSocket. |
| Training chatbot | `/api/training-chatbot` | Training-coaching ReAct chatbot over WebSocket. |
| Analyst chatbot | `/api/analyst-chatbot` | Athlete/coach trick-analysis ReAct chatbot over WebSocket (histograms, classify, frames, crop). |
| Video | `/api/video` | Uploads, streaming, frame/shift, cut, clips, cutter-configs, deletion, jobs. |
| Training | `/api/training` | Classes, extract/process/embed/promote, train/retrain, model registry, phase frames, jobs. |
| Crawler | `/api/crawler` | Instagram crawl, posts, QC, jobs. |

### 1.1 Routing facts (from `main.py`)

- Every slice router is included with `prefix="/api"`; each controller carries
  its own sub-prefix (e.g. `APIRouter(prefix="/video")`), so the final path is
  `/api/video/...`, `/api/training/...`, `/api/crawler/...`, `/api/tools/...`.
- Chatbot router → `prefix="/api/chatbot"`, endpoint `WS /ws/chat`
  → full path `/api/chatbot/ws/chat`.
- Training-chatbot router → `prefix="/api/training-chatbot"`, endpoint
  `WS /ws/training-chat` → full path `/api/training-chatbot/ws/training-chat`.
- Analyst-chatbot router → `prefix="/api/analyst-chatbot"`, endpoint
  `WS /ws/analyst-chat` → full path `/api/analyst-chatbot/ws/analyst-chat`.
- All three WebSocket routers are wired **best-effort**: if their dependencies
  cannot be imported, `main.create_app` skips them and logs
  `[startup] ... router not available` (the REST API still starts).
- CORS: `allow_origins=["*"]`, `allow_methods=["*"]`, `allow_headers=["*"]`,
  with `expose_headers` including `X-Total-Count` and the `X-Count-*` family.

### 1.2 Error envelope

`src/core/errors.py` registers a single handler for the `AppError` hierarchy.
Every domain error is returned as:

```json
{ "detail": "<human-readable message>" }
```

| Exception | HTTP status | Typical trigger |
| :--- | :--- | :--- |
| `BadRequestError` | 400 | Tool failure (crop range invalid, missing file, bad phase_frames). |
| `NotFoundError` | 404 | Entity or job not found. |
| `ConflictError` | 409 | Duplicate name, cannot delete video with children, cannot activate/approve in wrong state. |
| `ValidationError` | 422 | Domain validation (invalid status enum, non-`phases` histogram patch, unprocessed video selected…). |
| `ServiceUnavailableError` | 503 | LLM endpoint down (surfaces as a 503 WS frame in the training chatbot, §6). |
| `AppError` (base) | 500 | Unhandled app-level error. |

FastAPI's own request-validation failures (malformed body, missing fields,
type errors) return the standard **422** `{"detail": [...]}` envelope. The
chatbot WebSocket rate limiter returns a **429-equivalent** WS frame (see §4),
not an HTTP status.

### 1.3 Identifiers

- Path `{class_id}`, `{video_id}`, `{clip_id}`, `{config_id}`, `{post_id}`,
  `{run_id}`, `{job_id}`, `{temporal_id}` are strings.
  Mongo-backed IDs are **24-hex `ObjectId` strings**; `{run_id}` is a
  `YYYYmmdd_HHMMSS[-n]` string; `{job_id}` is an `ObjectId` string.

## 2. Shared job model & lifecycle

Almost every long-running operation (`cut`, `extract`, `process`, `embed`,
`promote`, `clip`, `train`/`retrain`, `crawl`, `upload`, `shift`, `delete`,
`delete_class`, `create`) is submitted as a **background job** and returns
`202` with `{"job_id": "..."}` (a few also return extra fields).

Jobs live in the Mongo `jobs` collection (`core/jobs.py`). A job document:

```json
{
  "_id": "64f…",
  "kind": "cut",                       // job type (see below)
  "entity_id": "<class_id or null>",
  "slice": "video",                    // video | training | crawler | tools
  "status": "running",                 // pending | running | done | failed | stopped
  "progress": 0.5,                     // 0.0 .. 1.0
  "result_json": null,                 // result payload when done
  "error": null,                       // error text when failed/stopped
  "description": null,                 // human summary when done
  "created_at": "2026-08-12T…Z",
  "finished_at": null
}
```

**Status machine:** `pending → running → done | failed | stopped`.

- `stopped` = cancelled (`POST /jobs/{id}/cancel`) or orphaned by a process
  restart (startup marks leftover `pending`/`running` jobs as `stopped`).
- Cancellation is cooperative: `POST …/jobs/{job_id}/cancel` sets a
  `cancel_requested` flag; the worker checks it between items and raises
  `JobCancelled`, typically rolling back partial work (clips, windows,
  embeddings, downloaded posts…). Only `pending`/`running` jobs can be
  cancelled (otherwise `409`).

**Job kinds** (by slice) → the `kind` field value:

| kind | slice | triggered by |
| :--- | :--- | :--- |
| `upload` | video | `POST /api/video/classes/{id}/videos` |
| `cut` | video | `POST /api/video/classes/{id}/cut` |
| `shift` | video | `POST /api/video/videos/{id}/shift` |
| `delete` | video | `POST /api/video/videos/delete` (batch) |
| `extract` | training | `POST /api/training/classes/{id}/extract` |
| `process` | training | `POST /api/training/classes/{id}/process` |
| `embed` | training | `POST /api/training/classes/{id}/embed` |
| `promote` | training | `POST /api/training/classes/{id}/promote` |
| `clip` | training | `POST /api/training/classes/{id}/clip` |
| `retrain` | training | `POST /api/training/classes/{id}/train` and `/retrain` |
| `create` | training | `POST /api/training/classes/jobs` |
| `delete_class` | training | `DELETE /api/training/classes/{id}` |
| `crawl` | crawler | `POST /api/crawler/classes/{id}/crawl` |
| `histogram_analysis` | tools | `POST /api/tools/histograms/analysis` |

Each slice exposes its own job-status router (identical shape, scoped to its
`slice`):

- `GET  /api/{slice}/jobs?status=&limit=` — list recent jobs for the slice.
- `GET  /api/{slice}/jobs/{job_id}` — one job.
- `POST /api/{slice}/jobs/{job_id}/cancel` — request cancellation (202).

(`{slice}` ∈ `video`, `training`, `crawler`, `tools`.)

> The training chatbot's `inspect_job` tool also normalises both the
> `pole_jobs` shape (chatbot worker queue) and the `core.jobs` shape (this
> section) because they share the `jobs` collection.

## 5. Tools slice (`/api/tools`)

The **tool** endpoints (`crop`, `shift`, `correct`) return the `ToolResponse`
envelope (`src/tools/schemas.py`):

```json
{ "success": true, "result": { "...": "..." }, "error": null }
```

On failure the controller raises an `AppError`, so the HTTP body is
`{"detail": "..."}` rather than a `ToolResponse` with `success=false`.

The **histogram** endpoints (`/api/tools/histograms/*`) are a MongoDB-backed
resource namespace and return **plain JSON** (`202 {job_id}` or the full
per-video document) — not the `ToolResponse` envelope.
Histogram production is a background job (`analysis`) plus read/patch
routes; see the Histogram endpoints subsection below.

> **Note on "histogram" / "similarity".** The `histogram` and `similarity`
> chatbot tools (see §6) call the processor (`pole_tools`/`pole_ml`) directly —
> they are not the REST `/api/tools/histograms/*` endpoints documented below.

### `POST /api/tools/crop`

**Purpose.** Trim a segment out of a source video (synchronous; writes the
output file to disk).

**Body** (`CropRequest`):

| Field | Type | Required | Default | Meaning |
| :--- | :--- | :--- | :--- | :--- |
| `src` | string (path) | yes | — | Source video path. |
| `start` | float ≥ 0 | yes | — | Segment start (seconds). |
| `end` | float ≥ 0 | yes | — | Segment end (seconds). |
| `out_dir` | string \| null | no | `null` | Output directory override (default `chatbot_output`). |
| `filename` | string \| null | no | `null` | Output filename override. |

**Response (200).** `result` = `CropResult`:

```json
{
  "success": true,
  "result": {
    "path": "/abs/chatbot_output/clip_123.mp4",
    "filename": "clip_123.mp4",
    "start": 0.5, "end": 2.0,
    "duration": 1.5, "source_duration": 9.7,
    "metadata": {}
  },
  "error": null
}
```

**Errors.** `400` (source missing or crop range invalid) → `{"detail": "…"}`.

**Example.**

```bash
curl -s -X POST http://localhost:8000/api/tools/crop \
  -H 'Content-Type: application/json' \
  -d '{"src":"/data/handspring.mp4","start":0.5,"end":2.0,"filename":"api_crop.mp4"}'
```

### `POST /api/tools/shift`

**Purpose.** Re-cut a segment from a source video (identical shape to `crop`).

**Body** (`ShiftRequest`): same fields as `CropRequest` (`src`, `start`, `end`,
`out_dir?`, `filename?`).

**Response (200).** `result` = `ShiftResult` (same shape as `CropResult`).

**Errors.** `400` (source missing or range invalid).

### `POST /api/tools/correct`

**Purpose.** Detect pose issues on a single frame and produce a red/green
correction overlay image.

**Body** (`CorrectRequest`):

| Field | Type | Required | Default | Meaning |
| :--- | :--- | :--- | :--- | :--- |
| `video_path` | string (path) | yes | — | Video to correct. |
| `frame_number` | int ≥ 0 | yes | — | Frame to correct. |
| `out_dir` | string \| null | no | `null` | Output directory override. |

**Response (200).** `result`:

```json
{
  "success": true,
  "result": {
    "frame": 42,
    "issues": ["knee_valgus"],
    "frame_path": "/abs/chatbot_output/frame_42.jpg",
    "overlay_path": "/abs/chatbot_output/corrected_42.jpg"
  },
  "error": null
}
```

**Errors.** `400` — frame out of range, or tool failure.

### Histogram endpoints

The trick-metric histogram is a MongoDB-backed resource (the `skeleton_data`
DB). Production runs as a **background job**; per-video documents are read back
in full, partially patched (phase boundaries only), and summarized (read-only
stored summary). Per-video documents live in
`skeleton_data.skeleton_histograms` (**plural**, one doc per `video_id`, keyed
by `video_id`, idempotent delete+re-insert); the cohort statistics live in a
separate `skeleton_data.signal_histograms` collection (one doc per
`(trick_label, metric)`, see §10).

#### `POST /api/tools/histograms/analysis` — **202**

**Purpose.** Submit a background `histogram_analysis` job over a batch of
extracted clips. The job runs a **two-pass** pipeline (§8.7 A-8):

1. **Pass 1 (curves + cohort):** resample each video's 8 metric curves to 300
   points (100 per phase, `init`→`execution`→`exit`), then update the cohort
   `skeleton_data.signal_histograms` `mean`/`std` (element-wise, sample std
   `ddof=1`) for each `(trick_label, metric)`.
2. **Pass 2 (summary):** against the **updated** cohort, compute each video's
   signed z-scores (`(resampled − mean) / max(std, σ_floor)`), per-metric 0-100
   `scores` (`score = 100 · exp(−|z_mean| / 2)`), and `detections` for every
   point with `|z| > 1` (one extracted JPEG per detected point). The results
   are persisted on the per-video doc (`z_mean`, `scores`, `detections`).

**Body** (`HistogramAnalysisRequest`):

| Field | Type | Required | Default | Meaning |
| :--- | :--- | :--- | :--- | :--- |
| `video_ids` | list[string] | yes | — | Clip video IDs to analyze (extracted, with `phase_frames`). |

**Response (202).**

```json
{ "job_id": "64f…" }
```

Poll with `GET /api/tools/jobs/{job_id}`.

**Job result** (`result_json`, §8.7 A-7):

```json
{
  "processed": ["<A>", "<B>"],
  "skipped": [{ "video_id": "<C>", "reason": "no phase_frames" }],
  "failed": [{ "video_id": "<D>", "reason": "corrupt landmarks" }],
  "histograms": 2
}
```

**Error isolation (hard rule).** One video failing does **not** fail the job:
per-video failures are captured in `result_json.failed` (or `skipped`) and
surfaced in the job `description` ("Processed N, Skipped M, Failed K — …"); the
job itself ends `done`.

**Errors.** `422` — empty or invalid `video_ids` (mirrors the other batch
endpoints); per-video errors are isolated, not fatal (see above).

**Example.**

```bash
curl -s -X POST http://localhost:8000/api/tools/histograms/analysis \
  -H 'Content-Type: application/json' \
  -d '{"video_ids":["64f…A","64f…B"]}'
# → {"job_id":"64f…"}
```

#### `GET /api/tools/histograms/{video_id}`

**Purpose.** Return the full per-video histogram document from
`skeleton_data.skeleton_histograms`.

**Path param:** `video_id` (string, required).

**Response (200).**

```json
{
  "video_id": "64f…",
  "trick_label": "handspring",
  "total_frames": 100,
  "extraction_stride": 5,
  "phases": {
    "init": { "start": 0, "end": 25 },
    "execution": { "start": 26, "end": 70 },
    "exit": { "start": 71, "end": 99 }
  },
  "metrics": { "horizontal_speed": [0.0, "…"], "vertical_speed": [0.0, "…"], "…": "…" },
  "resampled": { "horizontal_speed": [0.0, "…"], "…": "…" },
  "z_mean": { "horizontal_speed": 0.42, "…": "…" },
  "scores": { "horizontal_speed": 81.0, "…": "…" },
  "detections": [
    { "index": 152, "phase": "execution", "metric": "vertical_speed",
      "z_score": 2.3, "frame": 58, "frame_image_path": "/abs/…/frame_58.jpg" }
  ],
  "generated_at": "2026-08-13T…Z"
}
```

> The cohort `mean`/`std` are **not** on this document — they live in
> `skeleton_data.signal_histograms` (see §10).

**Errors.** `404` — no histogram document for the video
(`{"detail": "histogram not found"}`).

**Example.**

```bash
curl -s http://localhost:8000/api/tools/histograms/64f…
```

#### `PATCH /api/tools/histograms/{video_id}`

**Purpose.** Partially update the **phase boundaries** (`phases`) of a histogram
document. No derived arrays are recomputed — re-run `histograms/analysis` to
refresh `resampled`/`z_mean`/`scores`/`detections`.

**Body** (`HistogramPhasesPatch`): the `phases` object, partial allowed:

```json
{
  "phases": {
    "init": { "start": 0, "end": 26 },
    "execution": { "start": 27, "end": 71 },
    "exit": { "start": 72, "end": 99 }
  }
}
```

(`phases.init` / `phases.execution` / `phases.exit` are each `{start, end}`;
any subset may be provided.)

**Response (200).** The updated histogram document.

**Errors.**

- `422` — any field other than `phases` present in the body
  (`metrics`/`resampled`/`z_mean`/`scores`/`detections`/unknown) →
  `{"detail": "only 'phases' may be patched"}`.
- `404` — no histogram document for the video.

**Example.**

```bash
curl -s -X PATCH http://localhost:8000/api/tools/histograms/64f… \
  -H 'Content-Type: application/json' \
  -d '{"phases":{"execution":{"start":27,"end":71}}}'
```

#### `GET /api/tools/histograms/summary/{video_id}`

**Purpose.** Read-only per-video **summary** endpoint (Phase 12, PLAN.md §9):
returns the summary fields the `histogram_analysis` job persisted on the
per-video `skeleton_histograms` doc — signed per-metric `z_mean`, per-metric
0-100 `scores`, `detections` (`|z| > 1`, one extracted JPEG each), and the
optional `critical_*` fields — **verbatim**. No recompute, no job, no frame
extraction at read time.

**Path param:** `video_id` (string, required). **No request body.**

**Response (200)** (`VideoSummary`):

```json
{
  "video_id": "64f…",
  "trick_label": "handspring",
  "z_mean": { "horizontal_speed": 0.42, "…": "…" },
  "scores": { "horizontal_speed": 81.0, "…": "…" },
  "detections": [
    { "index": 152, "phase": "execution", "metric": "vertical_speed",
      "z_score": 2.3, "frame": 58, "frame_image_path": "/abs/…/frame_58.jpg" }
  ],
  "critical_frame": 58,
  "critical_phase": "execution",
  "critical_metric": "vertical_speed"
}
```

(`critical_*` are optional — omitted when the stored doc has no detections.)

**Errors.**

- `404` — no histogram document for the video
  (`{"detail": "histogram not found"}`).
- `404` — histogram exists but the summary fields are absent (analysis never
  ran for the video) →
  `{"detail": "summary not available for '<id>'; run histograms/analysis first"}`.

**Example.**

```bash
curl -s http://localhost:8000/api/tools/histograms/summary/64f…
```

## 6. Chatbot — WebSocket (`/api/chatbot/ws/chat`)

**Purpose.** Turn-based conversational assistant for the video-analysis tools
(crop, shift, correct, histogram, similarity). Tools are executed via
`ToolsService`; `crop`/`shift` run as **jobs** (return a `task_id`) while the
others run synchronously.

> The WS **`analyze` tool has been removed** (with the REST `POST /api/tools/analyze`
> and the reference/threshold/attempt vertical). The **`histogram`** tool now
> calls the processor (`tools_service.histogram(...)` → `pole_tools`/`pole_ml`)
> **directly** — not the `/api/tools/histograms/*` REST endpoints.

**Protocol.** After accept, the server sends `{"type":"connected","ws_connection_id":W}`
so the client can correlate relayed job events.

Client → server frames:

| Frame | Meaning |
| :--- | :--- |
| `{"type":"message","message":"…"}` | Process one turn (session created lazily). |
| `{"type":"message","message":"…","session_id":S}` | Resume session `S` and process the message. |
| `{"type":"resume","session_id":S}` | Resume session `S` without a message. |

Server → client frames:

| Frame | Meaning |
| :--- | :--- |
| `{"type":"connected","ws_connection_id":W}` | Sent right after accept. |
| `{"type":"agent_reply","reply":"…","tool_calls":[… ]}` | After each turn. |
| `{"type":"session_resumed","session_id":S,"original_video":"…"}` | Reply to a successful `resume`. |
| `{"type":"error","error":"…",…}` | Protocol/rate-limit errors. |
| relaid job events (`job_started` / `job_progress` / `job_done` / `job_error`) | Only those whose `ws_connection_id` matches this connection. |

**Errors (WS frames, not HTTP).**

- Missing/malformed message → `{"type":"error","error":"expected {type: 'message', message: str}"}`.
- Rate limit exceeded → `{"type":"error","error":"Rate limit exceeded","retry_after":N}` (sliding window, keyed by connection; configurable via `CHATBOT_RATE_LIMIT_MAX` / `CHATBOT_RATE_LIMIT_WINDOW_S`; fail-open if Redis is down).
- `resume` without `session_id` → `{"type":"error","error":"resume requires a session_id"}`.
- `resume` of unknown session → `{"type":"error","error":"session 'S' not found"}`.
- Agent not configured → `{"type":"agent_reply","reply":"Chatbot is not configured on this server.","tool_calls":[]}`.

> On disconnect, an in-progress session is closed as `ABANDONED`.

### `WS /api/training-chatbot/ws/training-chat`

**Purpose.** Training-coaching assistant (`Pole-Train`) over the same wire
protocol. Tools: `hyperparameter_search`, `compare_models`, `dataset_stats`,
`inspect_job` — all **sync**, all backed by `TrainingFacade`. No worker thread
and no crop/confirm workflow in v1.

Wire frames are identical to §6 with two differences:

- `session_resumed.original_video` is always `""` (training has no video
  concept).
- **LLM-down fallback** (UC-AG-05): when the agent is missing or `agent.run`
  fails, the server sends
  `{"type":"error","error":"LLM unavailable","status":503,"fallback_advice":"…"}`
  and keeps the connection alive.

Training tool contracts (facade outputs, surfaced via `tool_calls`):

- `hyperparameter_search(classes?, mode="recommend")` →
  `{classes, recommendation:{epochs, learning_rate, window_size, batch_size, use_augmentation, use_class_weight}, rationale[], note, search_space{…}}`.
- `compare_models(mode?, status?, limit=10)` → `{runs[], count, best}` where each
  run is `{run_id, mode, status, classes[], window_count, accuracy, loss, created_at, active}`.
- `dataset_stats(labels?)` → `{labels[], total_windows, per_label{}, selected_windows, untrained_windows, quality_flags{…}}`.
- `inspect_job(job_id?, limit=10)` → `{job_id, type, status, progress, result, error, queue, description, created_at}` (or `{jobs[], count}` when listing).

### `WS /api/analyst-chatbot/ws/analyst-chat`

**Purpose.** Athlete/coach trick-analysis assistant (`Pole-Analyst`) over the
same wire protocol as §6 / the training chatbot. Tools (PAIML-POLE-API-051):
`histogram`, `classify`, `extract_frames`, `crop` — all **sync**, all backed by
`AnalystFacade`. No worker thread and no crop/confirm workflow in v1. The
analysis pipeline itself is started by the FE via
`POST /api/analysis/videos/{id}/analyze`; the chatbot interprets, classifies
and edits.

Wire frames are identical to the training chatbot:

- Client→server: `{"type":"message","message":"…"}` (optionally with
  `session_id`) and `{"type":"resume","session_id":S}`.
- Server→client: `connected`, `agent_reply`, `session_resumed`,
  `{"type":"error","error":"LLM unavailable","status":503,"fallback_advice":"…"}`
  (UC-AG-05, keeps the connection alive), and relayed job events
  (`job_started` / `job_progress` / `job_done` / `job_error`) whose
  `ws_connection_id` matches — the relay listener is wired from
  PAIML-POLE-API-052.
- `session_resumed.original_video` is `""` until the 051 tools attach one.
- Sessions are persisted (Redis + Postgres via `ChatbotSessionService`) and
  closed `ABANDONED` on disconnect.

### Metric codes (M-01..M-08)

The authoritative histogram signal set (`pole_tools.services.histogram.METRICS`),
used by the `/api/tools/histograms/*` endpoints (§5) and the `histogram`
chatbot tool:

| Code | Metric name |
| :--- | :--- |
| M-01 | `horizontal_speed` |
| M-02 | `vertical_speed` |
| M-03 | `angular_speed` |
| M-04 | `torso_tilt_speed` |
| M-05 | `wrist_stability` |
| M-06 | `hip_height` |
| M-07 | `body_tilt` |
| M-08 | `smoothness` |

> **Metric semantics (Phase 11, PO-confirmed).** `angular_speed` (M-03) is **true spin** — azimuth/yaw,
> the rotational velocity of the torso about the body's vertical axis (axial rotation about the pole),
> `d(atan2(x, z))/dt` (unwrapped). `torso_tilt_speed` (M-04) is the **inclination derivative** — the
> rate at which the spine tilts away from upright, `d(arccos(vec_y/|vec|))/dt`. `hip_height` (M-06) =
> hip-mid height ÷ torso length. `smoothness` (M-08) = inverse jerk `1/(1 + mean|d³pos/dt³|)`. The
> legacy joint-angle metrics (`hip_angle`/`knee_angle`/`shoulder_angle`) are **dropped** and
> `body_tilt_angle` is **renamed** `body_tilt` (see `PLAN.md` §8.7 A-2).

### Cohort statistics (`skeleton_data.signal_histograms`)

Cohort `mean`/`std` (300-pt arrays, element-wise, sample std `ddof=1`) are
stored in `skeleton_data.signal_histograms` — **one doc per `(trick_label,
metric)`**:

```json
{
  "trick_label": "handspring",
  "metric": "horizontal_speed",
  "mean": [0.0, "…" /* 300 pts */],
  "std": [1.0, "…" /* 300 pts */],
  "count": 12,
  "phase_bounds": { "init": [0, 99], "execution": [100, 199], "exit": [200, 299] },
  "generated_at": "2026-08-13T…Z"
}
```

These cohort stats are **not** denormalized into the per-video
`skeleton_histograms` doc (§5) — they live only in `signal_histograms`.

## 11. Ambiguities & omissions

1. **Location/naming.** The requested path `docs/app/pole_api/` does not exist;
   the canonical project directory is `docs/app/pola_api/` (matching the app
   name `pola_api`, the ticket prefix `POLA-API`, and `docs/app/pola_api/`).
   This file was therefore written to `docs/app/pola_api/POLE-API.md`. The
   filename `POLE-API.md` was kept verbatim from the request; renaming it to
   `POLA-API.md` would be more consistent with the repo conventions.

2. **Chatbot vs REST histogram.** The `histogram` and `similarity` chatbot
   tools (see §6) call the processor (`pole_tools`/`pole_ml`) directly — they
   are not the REST `/api/tools/histograms/*` endpoints documented in §5.

3. **Regenerated `flows.md` (Phase 11).** The previous version of
   `docs/app/pola_api/flows.md` referenced `POST /api/video/classes/{id}/uploads/{uid}/verify`,
   which no longer exists — uploads are now auto-verified by the background
   `upload` job — and wrote the single-video delete as `POST /api/video/videos/{id}`
   (actual route: `DELETE /api/video/videos/{id}`). Both were fixed by ticket
   `PAIML-POLA-API-020`; `flows.md` now also documents the histogram namespace.

4. **WebSocket routers are conditional.** If `pole_chatbot` / `pole_jobs`
   dependencies are unavailable, the two WS routers are not mounted (the REST
   API still starts). They are treated as experimental/best-effort slices.

5. **`/api/tools/correct`** depends on the MediaPipe pose model
   (`pose_model_path`); when the model file is missing, `/api/tools/health`
   reports `degraded` and the endpoint fails at runtime with a `400`/tool
   error.

6. **Response shapes** for ffprobe metadata (`GET …/videos/{id}/metadata`) and
   the cutter `result_json` depend on the underlying `pole_crop` / cutter
   libraries and are described at a representative level, not exhaustively.

7. **Histogram endpoints — canonical contract.** The `/api/tools/histograms/*`
   endpoints in §5 (`analysis`, `GET/PATCH {video_id}`, `summary`, `jobs`) are
   the documented reference contract for the histogram feature as implemented
   in Phase 11 and Phase 12. Implementation is tracked in `PLAN.md` §8
   (Phase 11, tickets `PAIML-POLA-API-002..020` under
   `docs/app/pola_api/phase-11-histogram-analysis/`) and §9 (Phase 12, tickets
   `PAIML-POLA-API-021..024` under
   `docs/app/pola_api/phase-12-histogram-summary/`). The read-only **summary**
   endpoint (`GET /api/tools/histograms/summary/{video_id}`, Phase 12) returns
   the stored summary and is documented in §5. The §10 metric table
   (M-01..M-08) and the `signal_histograms` cohort-stat schema are
   authoritative.
